# Slam

The terms (pog, face, log, notes, stack, pick up, slam, flip) are defined in the POGflow README. It is at `${CLAUDE_PLUGIN_ROOT}/README.md` (the top of the repo these skills are in), or at https://github.com/stephenholtz/POGflow. Read it first. Request: `$ARGUMENTS`

Where these steps leave something open, three things decide it: the pushed pog is kept true first, nothing but pogs is committed (step 9 names the one exception), and the user is told at once when either cannot be done.

1. **Helper.** If another agent launched you (a swarm subagent, a workflow step), you do not hold the pog. Write nothing. Put the face and log line you would have written in your report.
2. **Find the repo.** Look for a `pogs/` folder from the working directory upward, then in the repo the project's CLAUDE.md names. If there is none, say POGflow is not set up here, ask where `pogs/` is, and stop. From here use `git -C <repo>` and absolute paths.
3. **Update the clone.** `git fetch`, then `git merge --no-edit origin/main` (the branch's upstream, if it is not `main`). It fast-forwards when it can; a conflict inside a pog is handled as in step 10, and a merge that an uncommitted file stops, or that conflicts outside `pogs/`, as in step 11. Then re-read each pog from disk, not from memory.
4. **Name the pogs.** They are the pogs this session holds and has worked on since its last slam. A pog is made only on the user's word: when they ask for one, or say yes after you suggest one for work that is more than a one-off. Suggest once; without a yes, carry on with no pog. When making one, if a name in `pogs/` is a near match, ask. Otherwise make the file in the shape of the README's example, with the user's name in the Waiting label, and link its plan. Whenever a plan's work gets a pog, by a split too, add a link to the pog in the plan. If the plan has a line giving the work's status and that line has no date, put the date on it.
5. **Answers first.** Write the user's answer and the date beside its Q in Notes before acting on it. If it could fit two questions, quote the Q back and ask. A new question goes in Notes as a dated Q with an empty A before it is asked in chat.
6. **Face.** Rewrite the four lines so each is true now. A Waiting item keeps the date it was first asked. It leaves only with an A in Notes, or a log line saying it was dropped or moved to another pog in a split. Flip, park and reopen change State; flip only on the user's word, whether the work was finished or dropped, and the log line says which. Before a flip, ask once whether anything in Notes outlives the work, and name what you would keep. Ask it in chat only: it is not written as a Q, and no slam comes before it. The user answers nothing, now or later. Nothing: flip. Now: copy it to where the repo keeps such facts (its docs, or the plan), then flip; the pog keeps its notes. Later: State stays `open`, Next becomes "document: <what, where>, then flip", and the flip comes when that is done, without asking again. The copied text is ordinary work in the repo, not part of the slam's commit. Only the session that holds a pog splits it: a new pog and a line in both logs. What moves to the new pog is not fixed here: settle it with the user each time.
7. **Log.** Add one line on top, as `- <date> <machine> <id>: <what happened>`: the date from `date +%F`, the machine (the name the session was given at its start, else `hostname -s`), the session's id (the first 8 characters of `$CLAUDE_CODE_HOST_SESSION_ID` after `local_`, or of `$CLAUDE_CODE_SESSION_ID` where that is not set; left out if the session has neither), what happened and why it stopped, any code commits by id with "pushed" or "not pushed" (this repo's unpushed commits go out with the slam's push, except through step 11), and any work left uncommitted. A pog with nothing to say since its last log line (picked up and no work done, no answer, no face line changed) gets no log line and is left out of this slam.
8. **Check.** `git diff -- pogs/<file>` shows face lines changed, one log line added, and no old Log or Notes text lost. Two exceptions, and the log line says where the text went: text moved to the new pog in a split, and notes moved to a plan once that plan is committed and pushed. A new pog shows no diff: read the file. `grep -A3 '^\*\*State:\*\*' pogs/<file>` prints State, Tags, Waiting, Next in that order.
9. **Commit and push.** `git add -- <the pog files>`, then `git commit -m "pogs: <names>: <what happened>" -- <the same files>`. Naming the files commits them alone, whatever else is staged. A slam commits files under `pogs/` only. The one exception is the plan edited in step 4: add and commit it by path with the pogs, but only if that edit is its only change. If the plan has other changes, leave it uncommitted and say so in the report. `git show --stat HEAD` must list nothing else. Then `git push`.
10. **Push refused.** If the reason is anything other than being behind (a protected branch, no access), do not try again: say that the slam is committed and not pushed, and why. If the clone is behind: `git fetch`, `git merge --no-edit origin/main`, re-read each pog, push again. If the merge made a face untrue, fix it (steps 6 to 9) before the push. A conflict inside a pog means two sessions wrote it. Keep both sides' log lines and Notes, write one face that is true now, finish the merge with `git add -- <the pog>` and `git commit --no-edit` (no path: git refuses one during a merge), and show the user both faces.
11. **Blocked.** The merge is stopped by an uncommitted file, or it conflicts in a file outside `pogs/` (then `git merge --abort`). Leave that file alone, whoever's it is: never commit, change or discard it. The pogs still go out, through a clean copy of origin. `git worktree add --detach <dir> origin/main`, with `<dir>` a new folder outside the repo. Write the pogs there, on origin's copies (steps 4 to 8), and nowhere in this clone. Commit them by path with `git -C <dir>`, then `git -C <dir> push origin HEAD:main` and `git worktree remove <dir>`. If that push is refused because origin moved on, do this step again with a new folder. If a pog commit was already made in this clone, repeat it in the clean copy with `git -C <dir> cherry-pick <id>` instead of writing it again. Where the branch's upstream is not `main`, use it in place of `main`. Tell the user which file is in the way, and that this clone stays behind origin until it is cleared.
12. **Another session's pog.** An answer for a pog this session does not hold: write the A beside its Q, take that item out of Waiting, add one log line, and change nothing else in that pog. Commit that file by path as in step 9. If that file has uncommitted changes on this machine, do not touch it, and tell the user to give the answer in the session that holds it.
13. **Report.** Confirm the pogs reached origin: after `git fetch`, `git log -1 origin/main -- pogs/<file>` shows this slam's commit. Then send the question or the last message, with one line: which pogs were written, and whether the push landed.

## Never

- `git add -A`, `git add .`, `commit -a`, or a slam commit that carries a file the slam did not write.
- Commit a work file, to clear a blocked merge or for any other reason.
- Make a pog the user did not ask for or say yes to.
- Stash, reset, checkout, rebase or force-push. Discard or tidy another session's uncommitted changes.
- Write a pog another session holds, beyond the one answer in step 12.
- Rewrite or delete old log lines.
- Add a log line that says only that the pog was picked up or that nothing was done.
- Copy a plan's content into a pog, or keep where the work stands anywhere else as well (a shared status file, a plan's status line).
- Say "slammed" when the push did not land.
- Save slams up for the end, wait for a clean tree or a finished task, or ask leave for each slam.
- Create `pogs/` where there is none, or add locks, claim lines, extra face lines or frontmatter to a pog.
